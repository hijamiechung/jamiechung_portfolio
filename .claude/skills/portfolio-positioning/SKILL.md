# Portfolio Positioning

## What to do

1. Read `PORTFOLIO_STRATEGY.md` at the project root. It is the private source
   of truth for positioning, narrative, and project selection. If the file
   does not exist (e.g. a public clone without it), say plainly that
   positioning context is unavailable and stop — do not guess at or
   reconstruct a positioning strategy from the code alone.
2. Identify the intended narrative and the specific claims the strategy makes
   about the content under review (e.g. what a given project is supposed to
   demonstrate, what framing it should avoid).
3. Compare the actual content — page copy, case-study text, project
   selection, ordering — against that narrative.
4. Report, specifically:
   - Where the content supports the intended positioning, and why.
   - Where it contradicts or undercuts it (wrong framing, wrong emphasis,
     a claim the strategy explicitly warns against).
   - Generic portfolio language that could describe any designer's work,
     with no connection to the specific positioning.
   - Projects or sections that add breadth ("another skill I have") rather
     than reinforcing the core identity.

## What not to do

- Do not force every project into the same story. If a project doesn't
  support the positioning, say so directly rather than inventing a
  connection.
- Do not treat surface-level keyword matches (the right buzzwords) as
  evidence of alignment — the strategy cares about the underlying argument,
  not vocabulary.
- Do not copy or quote large verbatim blocks of `PORTFOLIO_STRATEGY.md` into
  your output — paraphrase the relevant point instead. The file is private;
  your output may end up in places the strategy document itself should not.
- Do not recommend rewrites here — that's `case-study-storytelling`'s job.
  This skill's job is diagnosis: does this content match the intended
  identity, or not.
